# Etherna Gateway CLI

Etherna Gateway CLI is a **.NET console application** (assembly name **`etherna`**, not a library) to interact with the Etherna Gateway. Commands: `chunk` (create swarm chunks locally, upload chunks from a directory), `download` (download a resource from Swarm), `postage` (create/inspect postage batches), `resource` (fund/defund/list Swarm resource budgets), `upload` (upload files and directories to Swarm, buying postage batches as needed). It authenticates users against the Etherna SSO server through the EthernaSdk clients.

## Build, run, test

Target framework is **.NET 10** with `TreatWarningsAsErrors=true` and `AnalysisMode=AllEnabledByDefault` (and `Nullable=enable`, `EnableNETAnalyzers=true`) — warnings break the build. `InvariantGlobalization=true` is set on the executable.

```bash
dotnet restore EthernaGatewayCli.sln
dotnet build EthernaGatewayCli.sln -c Release
dotnet run --project src/EthernaGatewayCli -- --help                      # root help text
dotnet run --project src/EthernaGatewayCli -- postage create -d 20 -t 365 # example command
```

There is no test project: `dotnet build` (warnings-as-errors) is the verification step. When adding logic worth covering, create `test/EthernaGatewayCli.Tests` mirroring the `src/EthernaGatewayCli` folder layout and follow the testing conventions below.

The project takes a `FrameworkReference` to `Microsoft.AspNetCore.App` (needed by the SDK's native "code" auth flow), so the ASP.NET Core Runtime is a runtime prerequisite alongside the .NET Runtime — release packages also ship in a `selfcontained` variant.

The **`Debug-DevEnv`** build configuration defines the `DEVENV` constant, which switches the `#if DEVENV` blocks in `Program.cs` to local dev services: SSO on `https://localhost:44379/`, gateway on `http://localhost:1633/`. Plain `Debug`/`Release` builds target the production Etherna endpoints from `EthernaUserClientsBuilder` defaults.

`nuget.config` adds the `ethernaMyget` feed (https://www.myget.org/F/etherna/api/v3/index.json) next to nuget.org — prerelease dependencies like `Etherna.CliHelper` and `EthernaSdk.Users.Gateway` come from there. Versioning is automatic via **GitVersion** (`GitVersion.MsBuild`, plus SourceLink). CI (`.github/workflows/publish-stable.yml`): tags `v*.*.*` run `dotnet publish` over a matrix of runtime identifiers (linux/macos/windows × x86/x64/arm/arm64, framework-dependent and self-contained) and attach the archives to the GitHub release.

## Architecture

Solution `EthernaGatewayCli.sln`, a single project: **`src/EthernaGatewayCli`** (root namespace `Etherna.GatewayCli`; project folder named `EthernaGatewayCli`, assembly `etherna`). Under the root, the namespace mirrors the folder path.

- `Program.cs` — the entry point: pre-parses the root options, wires DI (`AddCoreServices` + the CliHelper command tree + the EthernaSdk clients), then resolves and runs `EthernaCommand`.
- `Commands/` — the command tree, organized by domain: `EthernaCommand` (root, with `EthernaCommandOptions` holding the global options) and `Commands/Etherna/` with `ChunkCommand` (+ `Chunk/`), `DownloadCommand`, `PostageCommand` (+ `Postage/`), `ResourceCommand` (+ `Resource/`), `UploadCommand`.
- `Services/` — application services behind interfaces: `AuthenticationService` (sign-in via `IEthernaSignInService`, reports the authenticated user), `FileService` (MIME type detection via Mime-Detective), `PostageBatchService` (depth calculation and usable-batch resolution for uploads).
- `Models/GitHubDto/` — the release-check DTO; `Utilities/EthernaVersionControl.cs` — the GitHub release update check.

### Key cross-cutting points

- **Commands come from `Etherna.CliHelper`.** Each command is an `internal sealed class` extending `CommandBase` (or `CommandBase<TOptions>`), overriding `Description` and `ExecuteAsync(string[] commandArgs)`. The command tree is registered in `Program.cs` via `AddCliHelper<ConsoleIoService>().AddCommand<…>(subCommands => …)` — a new command must be added there, in its domain folder. Help text is generated by CliHelper; there are no manual help strings.
- **Options classes are declarative.** A `<Command>Options` class extends `CommandOptionsBase` and declares `Definitions` (the `CommandOption` list: flags, description, parse lambda, arg types) and `Requirements` (`OptionRequirementBase` rules: `ExclusiveOptionRequirement`, `RequireOneOfOptionRequirement`, `MinValueOptionRequirement`, …). Parsed values are exposed as properties with `private set`. Validation belongs in `Requirements`, not in the command body.
- **Etherna clients come from the EthernaSdk builders.** `AddEthernaUserClients` registers both authentication flows together; `AuthenticationService` chooses the flow at sign-in time through `AuthenticationServiceOptions.ApiKey`: without `-k/--api-key` the "code" grant flow opens a browser login (local redirect on port 11430), with it the api-key flow is used. Then `AddEthernaGatewayClient` registers `IGatewayService`, with `apiCompatibility` driven by `--bee` (Bee vs Beehive API) and `gatewayBaseUrl` by `--gateway-url`.
- **`Program.Main` parses root options before building the service provider** (see the `WORKAROUND` comment in `Program.cs` — an open workaround to be resolved, not a pattern to extend): some registrations still need parsed root options (the api key handed to `AuthenticationServiceOptions`, the gateway client compatibility and base url), so `EthernaCommandOptions.ParseArgs` runs upfront with a temporary `ConsoleIoService`, and args are parsed a second time inside `EthernaCommand.RunAsync(args)`. Removing it requires CliHelper exposing command-parsed options through DI, and a deferred `AddEthernaGatewayClient` configuration in the SDK.
- **Authentication is explicit per command.** A command requiring an authenticated user calls `await authService.SignInAsync()` at the start of its `ExecuteAsync`.
- **All console I/O goes through `IIoService`** (CliHelper's `ConsoleIoService`; commands use the inherited `IoService` property) — never `Console` directly.
- **Swarm value types come from the SwarmSdk libraries** (`BzzValue`, `PostageBatchId`, `SwarmHash`, `RedundancyLevel`, …); chunking comes from SwarmSdk's `IChunkService`, registered in `AddCoreServices`.
- **Update check on every run.** `EthernaCommand.RunAsync` compares the running version against the latest GitHub release via `EthernaVersionControl.CheckNewVersionAsync`; when a newer version exists, execution stops unless `-i/--ignore-update` is passed.
- **No `ConfigureAwait(false)`** — this is an application, and `CA2007` is disabled in `.editorconfig`. (This is the opposite of the Etherna SDK/library repos.)

# Coding Style

## General Principles

- Keep commits clean: only include changes strictly necessary for the task at hand.
- Keep `README.md` aligned: when a change touches commands, options, or run steps, update `README.md` in the same change (it embeds the `etherna --help` output).
- Never reference AI agents or assistants in commits or code — no agent names, no `Co-Authored-By` agent trailers, no "generated/assisted by" notes. Commit messages and code must read as the team's own work.
- Exceptions to these conventions are accepted when strictly necessary or when they significantly improve code quality. Justify with a comment where needed.
- All elements (usings, properties, methods, fields, enum members, etc.) are always alphabetically ordered within their respective sections.
- Prefer primary constructors whenever possible — not limited to DI services. A parameter needing a light transformation still qualifies: capture it and derive a field. Fall back to a classic constructor only when the body needs real logic that can't be expressed as a field initializer.
- Keep code clean: remove unused variables, dead code, and redundant imports.
- Don't extract a private helper method for logic used in a single place — inline it. Reserve helpers for code shared by two or more call sites (or when extraction materially clarifies an otherwise long, complex method).
- Every source file starts with the standard AGPL-3.0 copyright header (`// Copyright 2024-present Etherna SA` … see any existing file).

## Naming

- **Classes/Structs**: PascalCase (`CreateCommand`, `FundCommand`, `InfoCommand`)
- **Interfaces**: `I` prefix (`IAuthenticationService`, `IPostageBatchService`)
- **Async methods**: always `Async` suffix (`RunAsync`, `ExecuteAsync`, `SignInAsync`)
- **Properties**: PascalCase (`Depth`, `IgnoreUpdate`, `UseBeeApi`)
- **Private fields**: `_camelCase` only when backing a same-named property; otherwise plain `camelCase`
- **Primary constructor parameters**: `camelCase` without underscore
- **Constants**: PascalCase (`EthernaGatewayCliClientId`, `HttpClientName`)
- **Enums**: PascalCase type and members
- **Namespaces**: `Etherna.GatewayCli.<Feature>` mirroring the folder under the root namespace (e.g. `Etherna.GatewayCli.Commands.Etherna.Postage`)
- **Commands**: `<Action>Command` pattern
- **Options classes**: `<Command>Options` suffix (`CreateCommandOptions`, `FundCommandOptions`)
- **DTOs**: `Dto` suffix (`GitReleaseVersionDto`)

## Code Organization

- One class per file, filename matches class name
- Namespace mirrors folder structure exactly (under the `Etherna.GatewayCli` root namespace)
- Block-scoped namespaces: `namespace X { ... }` — NOT file-scoped
- Using directives at the top of the file, before the namespace block, always alphabetically ordered and kept to the minimum necessary
- No global usings — each file declares its own imports
- Commands organized by domain: `Commands/Etherna/Chunk/`, `Commands/Etherna/Postage/`, `Commands/Etherna/Resource/`

## Comments

Principal comments (generally multiline, important):
```csharp
// Capital start, ending period.
// Continued on next line if needed.
```

Secondary/separator comments:
```csharp
//no space, no capital, no ending period
```

Comment only what helps a future reader: non-obvious behavior, intent, or a gotcha. Do **not** write narration of your own reasoning or decisions — that belongs in the commit message / PR description, never in committed code. If the code and section comments already make the intent clear, add nothing.

XML doc comments (`///`) document the API where they aid understanding; they are not compiler-enforced.

## Member Ordering Within a Class

Use principal-style section comments to delimit groups (singular `// Constructor.` when there is only one), in this order:

```csharp
// Consts.
// Fields.
// Constructors.
// Properties.
// Methods.
// Protected methods.
// Helpers.
```

Options classes use their own sections: `// Definitions.` (the `Definitions`/`Requirements` overrides) followed by `// Options.` (the parsed value properties).

## Class Design

- `internal sealed` for command and service implementations:
  ```csharp
  internal sealed class CreateCommand(
      IAuthenticationService authService,
      IGatewayService gatewayService)
      : CommandBase<CreateCommandOptions>
  {
  }
  ```
- `sealed` for options classes, extending `CommandOptionsBase`
- Command pattern: `CommandBase<TOptions>` base with `Description` and `ExecuteAsync` overrides
- Primary constructors everywhere the constructor is a simple assignment

## Async Patterns

- Always suffix with `Async`
- `CancellationToken cancellationToken = default` as the optional last parameter (non-nullable, `default` — not `CancellationToken? = null`)
- Return `Task` or `Task<T>`, never `async void`
- **No `ConfigureAwait(false)`** — this is an application, and `CA2007` is disabled in `.editorconfig`

## Null Handling

- Nullable reference types enabled (`<Nullable>enable</Nullable>`)
- `ArgumentNullException.ThrowIfNull(param)` for parameter validation (no redundant name argument)
- `is null` / `is not null` (not `== null`)
- Prefer `null` over `default` as default value for optional parameters
- `??` and `??=` operators; throw expressions: `?? throw new InvalidOperationException()`

## Formatting

- Allman braces (opening brace on new line)
- 4-space indentation (2 spaces in `.csproj` files, per `.editorconfig`)
- Expression-bodied members for single expressions
- String interpolation for user output: `IoService.WriteLine($"Batch id: {batchId}")`
- LINQ method chains: one operation per line, aligned
- Blank line between member sections

## C# Language Features

- Pattern matching: `is`, `is not`, type patterns, property patterns
- Prefer a property pattern over a chain of `&&` that combines a type/null check with member accesses: it expresses the condition as a single declarative "shape" the value must match
- Switch expressions for multi-branch returns
- Primary constructors everywhere applicable
- Collection expressions: `[]`, `[..spread]`
- Prefer collection expressions over constructors to initialize any collection: `[]` not `new()`, `["a", "b"]` not `new List<string> { "a", "b" }`. Use a constructor only when a collection expression can't express the intent (e.g. presizing capacity with `new List<T>(capacity)`).
- Target-typed `new()` when type is clear from context (for non-collection types)
- Tuple deconstruction for multiple return values
- Use the `field` keyword for field-backed properties (e.g. lazy initialization) instead of declaring an explicit backing field: `public T Prop => field ??= Compute();`

## LINQ

- Method syntax preferred over query syntax
- Query syntax only for complex join/groupby with multiple `from` clauses
- Fluent chaining, one operation per line for readability

## Dependency Injection

- Constructor injection exclusively, via primary constructors
- Core services registered in `ServiceCollectionExtensions.AddCoreServices` (`AddTransient`)
- Commands registered by CliHelper's `AddCommand<…>` tree in `Program.cs`
- Etherna service clients registered via the EthernaSdk builder extension methods (`AddEthernaUserClientsWithCodeAuth`/`AddEthernaUserClientsWithApiKeyAuth` + `AddEthernaGatewayClient`)

## Testing (xUnit + Moq)

There is currently no test project — when adding tests, follow the conventions of the other Etherna repos:

- `[Fact]` for basic tests, `[Theory]` with `[MemberData]` for parameterized cases
- AAA pattern with section comments: `// Setup.`, `// Action.`, `// Assert.`
- xUnit assertions: `Assert.Equal()`, `Assert.NotNull()`, `Assert.Throws<T>()` / `Assert.ThrowsAsync<T>()`
- Moq for mocking (`new Mock<IIoService>()`)
- Mirror the folder layout of the project under test (`test/EthernaGatewayCli.Tests` mirroring `src/EthernaGatewayCli`)
